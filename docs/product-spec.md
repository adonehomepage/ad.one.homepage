# Cursor 개발 명세서: 독립형 분양 랜딩페이지 제작·운영 플랫폼

> 문서 목적: 이 문서 하나만 Cursor에 전달해도 제품의 목적, 확정된 기능, 금지된 기능, 화면 구성, 데이터 구조, 구현 순서, 검증 기준을 이해하고 개발을 시작할 수 있게 한다.
>
> 문서 성격: 서비스 기획서 + 제품 요구사항 정의서(PRD) + UI/UX 가이드 + 기술 설계서 + 운영 정책 + 구현 체크리스트.
>
> 제품 상태: 브랜드명, 운영 법인명, 대표 도메인, 카카오 채널명은 아직 확정되지 않았다. 환경변수와 설정 데이터로 분리하고, 현재 단계에서는 중립적인 임시 명칭을 사용한다.
>
> 가장 중요한 원칙: 기존 직방 서비스와 비슷한 사용성은 참고하되, 이 서비스는 **직방과 무관한 독립 제품**이다. 직방의 소스코드, 비공개 문서, 데이터베이스, 디자인, 템플릿, 이미지, 고객 데이터, 사내 저장소나 계정은 복사하거나 재사용하지 않는다.

## 0. Cursor에게 전달하는 최상위 작업 지시

당신은 독립적인 분양 홈페이지 제작 SaaS를 구현하는 시니어 제품 엔지니어다. 이 문서를 우선순위가 가장 높은 제품 명세로 사용한다.

1. 광고사 직원이 직접 분양 홈페이지를 만들고 즉시 발행할 수 있는 서비스를 만든다.
2. 서비스는 `공개 랜딩페이지`, `제작 편집기`, `운영 관리자`의 세 영역으로 구성한다.
3. 로그인은 관리자 초대를 받은 광고사 직원만 가능하다. 공개 회원가입과 광고주 계정은 만들지 않는다.
4. 초기에는 한 광고사의 여러 직원이 하나의 워크스페이스에서 전체 프로젝트와 리드를 함께 관리한다.
5. 완전히 새로 디자인한 분양 랜딩페이지 템플릿 2종을 준비한다.
6. 섹션은 기존 템플릿에 포함된 섹션을 **복제**한다. 신규 섹션을 추가하는 기능이나 `+ 섹션 추가` 버튼은 만들지 않는다.
7. 섹션은 원본당 최대 3개까지 복제하고, 순서 변경, ON/OFF, 복제본 삭제, GNB 동기화를 제공한다.
8. 편집 중인 작업본과 공개 중인 발행본을 분리한다. 수정 내용은 재발행하기 전까지 공개 URL에 반영되지 않는다.
9. 최근 발행 버전 5개까지 복구할 수 있어야 한다.
10. 기본 운영기간은 3개월이며, 담당자가 직접 `N개월`을 지정할 수 있어야 한다.
11. 만료 7일 전에 광고사 담당자와 광고주에게 알리고, 만료 시 즉시 비공개 처리하며, 만료 후 30일이 지나면 정리 대상으로 처리한다.
12. 관심고객이 등록되면 광고주 수신자에게 카카오 알림톡 또는 이메일로 실시간 안내한다. 수신자는 프로젝트당 최대 5명이다.
13. 관심고객 이름과 연락처는 정당한 접근권한이 있는 광고사 직원과 인증된 광고주 수신자에게 마스킹 없이 제공할 수 있으나, 동의·접근권한·수신자 검증·발송 이력·파기 정책을 반드시 구현한다.
14. 프로젝트 목록, 리드 목록 및 누적 메모, 알림 이력, 대시보드, 추적 통계, 광고주용 PDF 보고서를 포함한다.
15. 디자인 시스템은 첨부된 Toss 참고 디자인 시스템의 색상과 명확한 UX를 참고하되, **모든 글꼴은 반드시 Pretendard**를 사용한다.
16. 결제, 과금, 구독, 제작 신청, 검수 승인, FAQ, 광고주 로그인, 상담 상태 관리, 공개 회원가입은 출시 범위에 넣지 않는다.
17. 브랜드와 법인 정보가 없어도 개발·테스트는 가능하게 만들되, 개인정보 처리 주체와 실제 발송 채널이 없는 상태에서 실제 고객 개인정보를 수집하거나 상용 발송하지 않는다.
18. 구현은 실제 DB, 실제 인증, 실제 발행 상태, 실제 권한 검사, 실제 저장소 연동을 전제로 한다. 겉보기만 동작하는 목업이나 브라우저 localStorage만 사용하는 구현으로 완료했다고 판단하지 않는다.
19. 불명확한 값은 제품의 확정 정책인 것처럼 임의로 확정하지 말고, `설정 가능`, `추천 기본값`, `출시 전 확정 필요` 중 하나로 명시한다.
20. 모든 프로젝트·리드·파일·알림 데이터는 현재 하나의 광고사에서 사용하더라도 `organization_id`를 기준으로 분리한다.

## 1. 제품 정의

### 1.1 한 문장 정의

광고사 실무자가 분양 현장별 홈페이지를 직접 제작하고 즉시 발행한 뒤, 관심고객 접수·광고주 알림·운영기간·성과 리포트까지 한 서비스 안에서 관리하는 독립형 B2B 제작 플랫폼.

### 1.2 해결하려는 문제

- 분양 현장마다 홈페이지를 새로 외주 제작하거나 담당자에게 제작 요청해야 한다.
- 수정사항이 있을 때마다 커뮤니케이션과 승인 대기가 발생한다.
- 광고에서 사용할 URL, 이미지, 영상, 관심고객 등록폼, 개인정보 동의문을 따로 관리한다.
- 접수된 관심고객 정보를 광고주에게 수작업으로 전달한다.
- 현장별 홈페이지 만료, 연장, 관심고객, 광고 성과를 한 번에 파악하기 어렵다.
- 작업 도중 변경한 내용이 실제 광고에 노출될 경우 오류나 운영 사고가 발생할 수 있다.

### 1.3 핵심 가치

- **직접 제작:** 광고사 직원이 별도 제작 신청 없이 편집한다.
- **즉시 발행:** 승인이나 검수 대기 없이 담당자가 발행한다.
- **공동 운영:** 같은 광고사의 직원들이 프로젝트와 관심고객을 공동 관리한다.
- **안정적인 수정:** 작업본과 공개본을 분리한다.
- **빠른 상담 연결:** 인증된 광고주 담당자에게 관심고객 접수 내용을 즉시 전달한다.
- **통합 관리:** 만료, 리드, 알림 실패, 통계, PDF 보고서를 한 곳에서 관리한다.
- **독립적 운영:** 직방 시스템, 직방 도메인, 직방 계정, 직방 인프라와 완전히 분리한다.

### 1.4 서비스 사용자

| 사용자 | 서비스 로그인 | 주요 역할 | 비고 |
| --- | --- | --- | --- |
| 시스템 관리자 | 가능 | 직원 초대, 계정 정지, 설정 변경, 감사 로그 확인 | 광고사 내부 사용자 |
| 광고사 직원 | 가능 | 프로젝트 제작, 편집, 발행, 삭제, 리드·통계 관리 | 같은 워크스페이스에서 공동 운영 |
| 광고주 담당자 | 불가 | 관심고객 접수 및 만료 관련 알림 수신 | 프로젝트당 최대 5명 |
| 관심고객 | 불가 | 공개 홈페이지 조회 및 관심고객 등록 | 개인정보 동의 필요 |

### 1.5 사업 및 운영 전제

- 초기 고객은 광고사 1곳이다.
- 직원은 여러 명이며 개별 계정을 사용한다.
- 모든 활성 직원은 소속 광고사의 프로젝트와 관심고객을 공동으로 보고 운영한다.
- 직원에게 프로젝트별 세밀한 읽기/쓰기 권한을 나누는 기능은 초기 범위에 포함하지 않는다.
- 직원 초대, 계정 정지, 전역 설정은 시스템 관리자 역할로 제한한다.
- 필요하면 여러 직원을 시스템 관리자로 지정할 수 있다.
- 사업자명과 브랜드명은 추후 확정되므로 화면과 알림에 하드코딩하지 않는다.
- 홈페이지 건별 가격은 향후 10만~20만 원 수준을 검토할 수 있으나, 현재 제품에는 결제나 과금 기능을 구현하지 않는다.

### 1.6 용어

| 용어 | 의미 |
| --- | --- |
| 조직 / 워크스페이스 | 서비스를 사용하는 광고사 단위 |
| 프로젝트 / 홈페이지 / 현장 | 하나의 분양 현장을 위한 공개 랜딩페이지 |
| 작업본 / draft | 편집 중인 비공개 변경사항 |
| 공개본 / published | 공개 URL에서 실제 방문자에게 노출되는 발행 버전 |
| 섹션 | 히어로, 사업개요, 입지환경 등 템플릿 내부 콘텐츠 단위 |
| 복제본 | 기존 원본 섹션의 내용을 복사해서 만든 독립 섹션 |
| GNB | 랜딩페이지 상단 내비게이션 |
| 리드 / 관심고객 | 공개 홈페이지에서 이름과 연락처 등을 제출한 방문자 |
| 수신자 | 관심고객 및 만료 알림을 받을 광고주 담당자 |
| 보관기간 | 개인정보를 적법한 목적과 동의 범위 안에서 보유하는 기간 |

## 2. 확정 범위와 제외 범위

### 2.1 반드시 포함

- 관리자 초대 기반 직원 계정.
- 직원별 로그인, 로그아웃, 비밀번호 설정 및 재설정.
- 계정 즉시 정지와 세션 차단.
- 하나의 조직 내 프로젝트 및 리드 공동 관리.
- 프로젝트 생성, 편집, 공개, 비공개, 연장, 삭제.
- 신규 템플릿 2종.
- 히어로 이미지 및 영상 업로드.
- 기존 섹션 복제, 원본당 최대 3개.
- 섹션 순서 변경, ON/OFF, 복제본 삭제.
- 섹션과 GNB의 자동 연동.
- PC/모바일 미리보기.
- 자유 입력형 공개 URL slug.
- 작업본과 공개본 분리.
- 무제한 수정과 재발행.
- 최근 5개 공개 버전 복구.
- 기본 3개월 / 직접 지정 N개월 운영기간.
- 만료 7일 전 광고사·광고주 알림.
- 만료 즉시 비공개 및 만료 후 30일 정리.
- 관심고객 등록폼과 현장별 추가 질문 설정.
- 관심 타입 선택형 폼 지원.
- 관심고객 목록, 검색, 프로젝트 필터, 누적 메모.
- 프로젝트당 광고주 수신자 최대 5명.
- 수신자별 카카오 알림톡 또는 이메일 선택.
- 광고주 연락처/이메일 소유 확인 및 변경 이력.
- 관심고객 등록 시 광고주 대상 즉시 알림.
- 알림 성공·실패·재시도 이력.
- 방문, 순 방문, 전화 클릭, 문의 등록, 유입경로, UTM, 전환율 추적.
- 광고주에게 공유 가능한 PDF 성과 보고서.
- 개인정보 동의, 처리방침, 접근제어, 감사 로그, 보관·파기 정책.
- 실제 배포, DB, 파일 저장소, 백업, 스케줄 작업.

### 2.2 출시 범위에서 제외

- PG 결제, 카드 결제, 정기구독, 세금계산서 자동화.
- 건별 요금 결제 화면과 요금제 선택 화면.
- 외부 광고주 회원가입과 광고주 전용 대시보드.
- 공개 회원가입 및 누구나 가입할 수 있는 SaaS 온보딩.
- 제작 신청, 제작 요청 접수, 담당자 승인, 검수 대기.
- FAQ / 자주 묻는 질문 섹션 또는 FAQ 관리 기능.
- 기존 템플릿에 없는 임의의 신규 섹션 추가.
- 상담 상태 단계 관리: 예) 신규, 상담 중, 계약 완료.
- 광고 소재 심사, 분양광고 문구의 자동 법률 검수.
- CRM 전체 구축, 영업 파이프라인, 매출 관리.
- 월 구독 정산, 매출 대시보드, 공동사업 정산.
- 관리자 승인을 거쳐야만 홈페이지가 공개되는 흐름.
- 직방 서비스 계정, 현장 DB, 직방 현장명과 연동되는 URL.
- 사용자별 커스텀 루트 도메인을 자동 구매하거나 생성하는 기능.
- 비즈프로필, 분양상담사 입점, 견적 시스템 등 다른 제품 기능.

### 2.3 해석 우선순위

충돌하는 설명이 있으면 다음 순서로 해석한다.

1. 이 문서에 적힌 사용자 확정 요구사항.
2. 개인정보 및 발송에 관한 법령, 보안, 발송 사업자 정책.
3. 기존 제작·운영 PDF 가이드.
4. 첨부된 디자인 시스템의 참고 원칙.
5. 기술적인 추천 기본값.

예: 참고 디자인 시스템은 `Toss Product Sans`를 언급하지만, 사용자가 명시적으로 **Pretendard**를 지정했으므로 실제 서비스는 Pretendard를 사용한다.

## 3. 엔드투엔드 사용자 흐름

### 3.1 직원 초대와 로그인

1. 시스템 관리자가 직원 이름과 이메일을 입력한다.
2. 시스템은 만료기간이 있는 1회성 초대 링크를 발송한다.
3. 초대받은 직원이 비밀번호를 설정하고 계정을 활성화한다.
4. 직원이 로그인하면 소속 조직의 대시보드로 이동한다.
5. 정지된 계정은 로그인할 수 없고, 기존 로그인 세션도 즉시 무효화된다.

### 3.2 프로젝트 제작과 발행

1. 직원이 `홈페이지 만들기`를 선택한다.
2. 프로젝트명, 공개 URL 텍스트, 운영기간을 입력한다.
3. 운영기간은 기본 `3개월`로 미리 선택되어 있다.
4. 필요하면 `직접 입력`을 선택하고 N개월을 입력한다.
5. 준비된 템플릿 2종 중 하나를 선택한다.
6. 프로젝트의 초기 작업본을 생성한다.
7. 편집기에서 문구, 이미지, 영상, 섹션, GNB, 관심고객폼을 편집한다.
8. PC·모바일 미리보기로 결과를 확인한다.
9. `발행하기`를 누르면 URL이 공개되고 운영기간 계산이 시작된다.
10. 이후 수정은 작업본에만 저장되며 `재발행`해야 공개 URL에 반영된다.

### 3.3 관심고객 등록과 전달

1. 방문자가 광고 링크를 통해 공개 랜딩페이지에 접속한다.
2. 페이지 조회, 유입 출처, UTM 정보를 수집 정책 범위 안에서 기록한다.
3. 방문자가 이름, 연락처, 선택 질문 및 문의 내용을 입력한다.
4. 개인정보 수집·이용 동의와 필요한 경우 제3자 제공 동의를 각각 확인한다.
5. 서버가 폼과 동의 상태를 검증한 후 리드를 DB에 저장한다.
6. 저장이 성공하면 알림 작업을 비동기 큐에 등록한다.
7. 프로젝트에 연결된 인증 완료 광고주 수신자에게 각자의 채널로 알림을 발송한다.
8. 광고사 직원은 관리자 리드 목록에서 등록 내용을 확인하고 메모를 추가한다.
9. 발송 실패는 관리자 대시보드와 발송 로그에 나타난다.

### 3.4 운영 종료

1. 운영 종료 7일 전에 광고사 담당자와 광고주에게 만료 예정 알림을 보낸다.
2. 담당자가 기간을 연장하면 새 만료일을 계산하고 변경 기록을 남긴다.
3. 연장하지 않으면 만료 시각에 공개 페이지를 즉시 비공개 처리한다.
4. 만료된 프로젝트는 내부에서 확인할 수 있으나 신규 공개 리드는 받지 않는다.
5. 만료 후 30일이 지나면 공개본, 전용 파일, 캐시 및 관련 데이터를 정책에 따라 정리한다.
6. 개인정보의 별도 보관기간은 실제 동의 문구와 법적 근거에 따라 독립적으로 판단한다.

## 4. 권한, 인증, 조직 구조

### 4.1 조직 모델

- 초기 UI에서는 조직 전환 기능을 만들지 않아도 된다.
- DB의 모든 주요 리소스는 `organization_id`를 포함한다.
- 현재 광고사 1곳만 사용하더라도 향후 서비스 확장을 고려해 조직 간 데이터 경계를 설계한다.
- 프런트엔드에서 전달한 `organization_id`만 신뢰하지 말고 현재 세션과 조직 멤버십을 서버에서 검증한다.
- 서로 다른 조직의 리드, 파일, 통계, 수신자에 접근할 수 없어야 한다.

### 4.2 역할

#### SYSTEM_ADMIN

- 모든 프로젝트 관련 공통 권한.
- 직원 초대, 재초대, 초대 취소.
- 직원 정지 및 정지 해제.
- 직원 관리자 권한 부여/회수.
- 서비스 환경설정 및 기본 보관기간 설정.
- 알림 채널 연결 상태 확인.
- 개인정보 접근 및 활동 로그 조회.
- 조직 내 마지막 활성 시스템 관리자를 정지하거나 권한 해제할 수 없음.

#### MEMBER

- 프로젝트 생성, 편집, 미리보기, 발행, 재발행, 비공개, 연장, 삭제.
- 같은 조직의 모든 프로젝트 조회.
- 같은 조직의 모든 리드 조회 및 메모 추가.
- 수신자 등록·수정·비활성화.
- 통계 조회, 파일 다운로드, PDF 생성.
- 관리자 전용 직원 관리 및 전역 보안 설정에는 접근 불가.

> 사용자의 “모든 직원이 권한을 가진다”는 요구는 **프로젝트와 리드에 대한 공동 운영 권한**으로 해석한다. 계정 정지나 전역 설정은 시스템 관리자 기능이며, 필요한 직원은 시스템 관리자 역할로 지정할 수 있다.

### 4.3 계정 상태

```text
INVITED → ACTIVE → SUSPENDED
    └──── EXPIRED
```

- `INVITED`: 초대 메일이 발송되었으나 가입을 완료하지 않음.
- `ACTIVE`: 정상 로그인 및 사용 가능.
- `SUSPENDED`: 즉시 접근 차단, 기존 세션 무효화.
- `EXPIRED`: 초대 링크 유효기간 종료. 관리자가 재초대 가능.

### 4.4 인증 세부 요구사항

- 이메일 기반 로그인.
- 비밀번호 설정 및 재설정.
- 로그인 오류는 계정 존재 여부를 과도하게 드러내지 않는 방식으로 처리.
- 반복 실패에 대한 속도 제한.
- 비밀번호는 직접 저장하지 않고 인증 공급자의 안전한 해시 체계를 사용.
- 인증 토큰, 서비스 롤 키, 알림 API 키는 브라우저로 노출하지 않음.
- 로그아웃 및 계정 정지 시 세션 검증을 서버에서 수행.
- 초대 링크는 1회 사용 또는 재사용 방지 정책 적용.
- 초대, 활성화, 정지, 정지 해제, 권한 변경을 감사 로그에 기록.

## 7. 프로젝트 생성과 관리

### 7.1 프로젝트 생성 필드

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| 프로젝트명 / 현장명 | 예 | 관리자 목록과 공개 페이지의 기본 이름 |
| 공개 URL 텍스트 | 예 | 현장명과 자동 연동하지 않는 독립 입력값 |
| 템플릿 | 예 | 신규 템플릿 2종 중 하나 |
| 운영기간 | 예 | 기본 3개월, 직접 입력 N개월 |
| 대표 이미지 | 아니오 | 관리자 썸네일 및 공유 이미지에 사용 가능 |
| 광고사 담당자 | 아니오 | 만료 및 운영 관련 알림 수신 대상 |
| 광고주 정보 | 발행 시 필요 | 개인정보 처리 및 알림 발송 설정에 사용 |
| 광고주 수신자 | 리드 발송 시 필요 | 프로젝트당 최대 5명 |

### 7.2 프로젝트 목록

- 프로젝트명.
- 공개 URL 및 복사 버튼.
- 상태 배지.
- 선택한 템플릿.
- 생성일 / 최초 발행일 / 최근 수정일.
- 만료일 및 D-day.
- 리드 수.
- 담당 직원.
- 최근 발행 버전.
- 빠른 액션: 편집, 미리보기, 공개 URL 열기, 연장, 비공개, 삭제.

### 7.3 목록 필터와 검색

- 프로젝트명 검색.
- URL slug 검색.
- 상태 필터.
- 템플릿 필터.
- 만료 예정 필터.
- 생성일 또는 발행일 정렬.
- 리드 수 정렬은 선택적 확장.
- 서버 페이지네이션 또는 안정적인 커서 페이지네이션.

### 7.4 프로젝트 상태

```text
                   ┌──────────────┐
                   │    DRAFT     │
                   └──────┬───────┘
                          │ 최초 발행
                          ▼
                   ┌──────────────┐
          ┌────────│  PUBLISHED   │◀─────────┐
          │        └──────┬───────┘          │
          │ 수동 비공개       │ 기간 만료          │ 재공개 / 연장
          ▼               ▼                  │
   ┌──────────────┐ ┌──────────────┐         │
   │    PAUSED    │ │   EXPIRED    │─────────┘
   └──────┬───────┘ └──────┬───────┘
          │ 삭제             │ 삭제 또는 30일 경과
          ▼                 ▼
             ┌──────────────────┐
             │ PENDING_DELETION │
             └────────┬─────────┘
                      │ 보관·파기 정책 충족
                      ▼
                 ┌─────────┐
                 │ DELETED │
                 └─────────┘
```

#### DRAFT

- 아직 한 번도 발행되지 않음.
- 공개 URL은 방문자에게 노출되지 않음.
- 운영 시작일은 아직 확정되지 않음.

#### PUBLISHED

- 공개 URL에서 마지막 발행 버전을 제공.
- 공개 중에도 작업본 수정 가능.
- 작업본 변경 유무를 별도 `has_unpublished_changes`로 표시.

#### PAUSED

- 담당자가 수동으로 즉시 비공개한 상태.
- 공개 URL에서는 비공개 또는 종료 안내 화면 제공.
- 내부 편집과 재공개는 정책에 따라 가능.

#### EXPIRED

- 운영기간 만료.
- 공개 URL과 신규 관심고객 접수 즉시 차단.
- 만료 후 30일 정리 일정 계산.
- 담당자가 기간을 연장하면 다시 공개할 수 있음.

#### PENDING_DELETION / DELETED

- 수동 삭제 또는 만료 후 정리 대상으로 전환.
- 공개 URL은 즉시 차단.
- 파일, 공개본, CDN 캐시, 리드 개인정보는 각각의 보관정책에 따라 정리.
- 삭제 실행자, 실행 시각, 대상 프로젝트를 감사 로그에 기록.

### 7.5 공동 편집 충돌

- 여러 직원이 동시에 편집할 수 있으므로 `draft_revision` 또는 `updated_at` 기반 낙관적 잠금을 사용한다.
- 다른 직원이 먼저 저장한 경우 조용히 덮어쓰지 않는다.
- `다른 담당자가 먼저 수정했습니다. 최신 작업본을 불러오세요.`와 같이 안내한다.
- 실시간 다중 커서 협업은 초기 범위에 포함하지 않는다.

## 8. 공개 URL과 도메인 정책

### 8.1 기본 형식

```text
https://[서비스도메인]/[사용자가-입력한-텍스트]
```

예시:

```text
https://example.com/루미에르센트럴
https://example.com/lumiere-central
https://example.com/prime84
```

### 8.2 확정 원칙

- 프로젝트명이나 현장명과 자동으로 묶지 않는다.
- 담당자가 URL 텍스트를 직접 입력한다.
- 한글, 영문, 숫자, 하이픈을 허용한다.
- 한글 slug는 브라우저 내부에서 URL 인코딩될 수 있으므로 화면에서는 읽기 쉬운 문자열로 보여준다.
- 양쪽 공백을 제거한다.
- Unicode 정규화는 NFC를 권장한다.
- 영문 대소문자는 중복 판단 시 동일한 문자열로 취급하는 것을 권장한다.
- 다른 프로젝트가 사용 중인 slug를 중복 사용할 수 없다.
- `/`, `?`, `#`, 제어 문자 등 URL 경로 구조를 바꾸는 문자는 허용하지 않는다.

### 8.3 예약어

```text
admin
api
login
logout
invite
privacy
terms
settings
assets
static
_next
favicon.ico
robots.txt
sitemap.xml
```

예약어 목록은 코드와 DB 검증 양쪽에서 관리한다.

### 8.4 중요한 도메인 설명

`희망텍스트.com`을 사용자가 임의로 입력한다고 해서 새로운 `.com` 도메인이 자동으로 생성되는 것은 아니다. 루트 도메인은 실제 등록, 소유권 확인, DNS 설정, HTTPS 인증서 발급이 필요하다.

이번 출시에서는 다음을 구현한다.

```text
운영사가 보유한 서비스 도메인 + 사용자가 원하는 URL 경로
```

프로젝트별 독립 도메인 구매 또는 외부 사용자 도메인 연결은 미래 확장으로만 남긴다.

### 8.5 URL 변경

- 최초 발행 전에는 자유롭게 변경할 수 있다.
- 발행 후 URL 변경은 기존 광고 링크가 깨질 수 있으므로 기본 정책은 변경 잠금으로 둔다.
- 향후 변경을 허용하려면 명시적인 경고, 기존 URL 리디렉션 정책, 중복 검사, 변경 이력이 필요하다.
- 사용자가 별도 승인하지 않은 상태에서 무음으로 URL을 변경하거나 이전 주소를 폐기하지 않는다.

### 8.6 삭제한 URL의 재사용

- 삭제 직후 기존 slug를 다른 현장에 즉시 재할당하지 않는 것을 권장한다.
- 이전 광고 링크가 살아 있는 상태에서 다른 현장 페이지가 노출되면 방문자 혼동이나 개인정보 오접수가 발생할 수 있다.
- 재사용 대기기간은 운영 설정으로 관리하고, 자동 재사용 여부는 담당자 확인 후 결정한다.
- 운영 측에서 별도 정책을 확정하기 전까지는 삭제된 slug를 예약 상태로 유지하는 것이 안전하다.

## 9. 신규 랜딩페이지 템플릿 2종

### 9.1 공통 원칙

- 템플릿은 완전히 새롭게 디자인한다.
- 직방의 시각 디자인, 레이아웃, 컴포넌트, 이미지, 문구를 복제하지 않는다.
- 템플릿 내부 콘텐츠는 프로젝트별로 독립 저장한다.
- 공개 홈페이지는 모바일과 데스크톱에서 모두 자연스럽게 동작해야 한다.
- 분양 정보가 명확하고 고급스럽게 전달되어야 한다.
- FAQ 섹션은 포함하지 않는다.
- 섹션의 조합은 초기 템플릿이 제공하는 범위 안에서만 조정한다.

### 9.2 템플릿 A: 이미지 중심형

- 밝고 정돈된 분양 브랜드 사이트.
- 대형 히어로 이미지.
- 명확한 현장명과 핵심 카피.
- 사업개요 / 입지환경 / 프리미엄 / 갤러리 / 관심고객 섹션.
- 부동산 분양 현장의 신뢰감과 정보 접근성을 우선.

### 9.3 템플릿 B: 영상 지원형

- 히어로 영역에서 이미지 또는 영상 모드를 선택할 수 있는 구성.
- 영상 선택 시 포스터 이미지 및 모바일 대체 이미지 설정.
- 영상은 자동재생 환경을 고려해 기본적으로 음소거하고 반복 재생.
- 브라우저 정책으로 자동재생이 차단되면 포스터 이미지를 표시.
- 정보 섹션은 템플릿 A와 다른 신규 레이아웃으로 구성.

### 9.4 초기 템플릿 섹션 예시

```text
1. 히어로
2. 사업개요
3. 입지환경
4. 프리미엄 / 특장점
5. 시설 / 갤러리
6. 타입 / 평면 정보
7. 오시는 길 / 위치 정보
8. 관심고객 등록폼
9. 법적 고지 및 사업 주체 정보
```

위 목록은 구현용 기본 제안이며, 실제 디자인 확정에 따라 세부 섹션명은 조정 가능하다. **새로운 종류의 섹션을 편집기에서 임의 추가하는 기능은 포함하지 않는다.**

### 9.5 공개 랜딩페이지 필수 요소

- 상단 GNB.
- 히어로 이미지 또는 영상.
- 프로젝트명과 핵심 카피.
- 현장별 기본 정보.
- 전화 연결 CTA.
- 관심고객 등록 CTA.
- 실제 동의 문구가 포함된 관심고객 폼.
- 광고주/시행 관련 법적 고지 및 개인정보 처리 정보.
- 모바일 터치 조작과 읽기 쉬운 텍스트 크기.

### 9.6 광고성 표시와 현장 정보

- 실제 사업 주체, 현장명, 공급 정보, 광고 문의처는 광고사 담당자가 입력한다.
- 확정되지 않은 정보나 추정 데이터를 시스템이 사실처럼 자동 생성하지 않는다.
- 분양 광고 문구 및 현장 고지의 최종 적법성은 광고사·광고주가 확인할 수 있도록 입력 필드를 제공한다.
- 시스템이 실제 사실을 보증하거나 분양 조건을 대신 검증하는 기능은 포함하지 않는다.

## 10. 제작 편집기 상세 명세

### 10.1 데스크톱 레이아웃

```text
┌────────────────────────────────────────────────────────────────────┐
│ 프로젝트명 | 저장 상태 | PC / 모바일 | 미리보기 | 발행 / 재발행      │
├──────────────────┬───────────────────────────────┬─────────────────┤
│ 섹션 목록         │ 랜딩페이지 미리보기             │ 선택 섹션 설정   │
│ 드래그 정렬       │ 실제 템플릿 렌더링              │ 텍스트          │
│ ON / OFF         │ 실제 공개본과 동일한 UI          │ 이미지 / 영상    │
│ 복제             │ 반응형 뷰 전환                  │ 링크 / 버튼      │
│ 복제본 삭제       │                               │ GNB 표시         │
└──────────────────┴───────────────────────────────┴─────────────────┘
```

### 10.2 상단 액션

- 프로젝트명.
- 현재 저장 상태: `저장됨`, `저장 중`, `저장 실패`, `미발행 변경사항 있음`.
- PC / 모바일 미리보기 전환.
- 새 탭 미리보기.
- 공개 페이지 열기.
- 최초 발행 또는 재발행.
- 버전 기록 진입.
- 나가기 전에 저장하지 않은 변경사항 경고.

### 10.3 좌측 섹션 패널

- 현재 템플릿에 포함된 섹션을 순서대로 표시.
- 각 섹션의 제목 표시.
- 활성 / 비활성 토글.
- 드래그 핸들 또는 접근 가능한 위/아래 이동 버튼.
- 선택 섹션 복제 버튼.
- 복제본 삭제 버튼.
- 원본별 현재 복제 개수와 최대 개수 표시.
- 필수 섹션은 삭제 불가.
- 허용되지 않은 신규 섹션 추가 버튼을 노출하지 않음.

### 10.4 중앙 미리보기

- 작업본 데이터를 기반으로 실제 랜딩페이지를 렌더링.
- PC와 모바일 너비를 각각 확인.
- 실제 폰트, 이미지, 색상, GNB, 폼을 표시.
- 편집 중인 섹션을 시각적으로 하이라이트 가능.
- 미리보기에서 폼 제출은 실제 리드를 생성하지 않도록 구분.
- 미리보기 URL에는 인증 또는 만료되는 서명 토큰 사용.
- 비공개 작업본이 검색엔진에 노출되지 않도록 `noindex` 처리.

### 10.5 우측 속성 패널

선택한 섹션의 종류에 따라 아래 항목 중 필요한 속성을 제공한다.

- 제목 / 소제목.
- 본문 텍스트.
- 버튼 문구.
- CTA 링크 또는 전화번호.
- 이미지 업로드.
- 영상 업로드.
- 영상 포스터 이미지.
- 이미지 대체 텍스트.
- 데스크톱 / 모바일 이미지 크롭 또는 위치.
- 배경 / 텍스트 색상: 템플릿이 허용하는 범위.
- GNB 표시 여부.
- GNB 라벨.
- 표시 순서.
- 카드 / 목록 반복 콘텐츠.
- 관심 타입 옵션.
- 현장별 추가 질문.

### 10.6 저장 방식

- 자동저장 또는 명시적 `저장` 중 하나를 구현하되 저장 상태를 분명히 표시한다.
- 잦은 입력에 대한 debounce 처리를 적용한다.
- 저장 실패 시 사용자가 내용을 잃지 않도록 재시도 UI를 제공한다.
- 서버 저장에 성공해야 작업본을 저장된 상태로 표시한다.
- 자동저장되더라도 공개본은 재발행 전까지 변경하지 않는다.

### 10.7 콘텐츠 제한

- 광고사가 스스로 콘텐츠를 편집할 수 있도록 과도한 제품 정책 제한을 두지 않는다.
- 다만 보안과 안정성에 필요한 파일 형식, 최대 업로드 용량, 네트워크 요청 제한은 설정 가능하게 두고 사용자에게 명확히 설명한다.
- 사용자 입력 HTML을 그대로 실행하지 않는다.
- 외부 iframe, script 삽입을 무제한 허용하지 않는다.
- 위험한 HTML 또는 URL은 정제하고 허용 목록 기반으로 처리한다.

## 11. 섹션 복제 로직

### 11.1 가장 중요한 제품 규칙

이 서비스의 기능은 `섹션 추가`가 아니라 `섹션 복제`다.

금지 예시:

```text
+ 섹션 추가
+ 새 블록 추가
빈 섹션 만들기
섹션 라이브러리에서 신규 유형 선택
```

권장 예시:

```text
선택 섹션 복제
복제하기
복제본 1 / 3
```

### 11.2 복제 동작

1. 사용자가 원본 섹션 또는 기존 복제본을 선택한다.
2. 시스템이 최초 원본의 `root_section_id`를 확인한다.
3. 해당 원본 아래에 이미 존재하는 복제본 수를 계산한다.
4. 복제본 수가 3개 이상이면 더 이상 복제하지 않는다.
5. 선택된 섹션의 제목, 문구, 콘텐츠 데이터, 이미지 참조, 영상 참조, 레이아웃 설정, 노출 설정을 복사한다.
6. 새로운 섹션 ID와 고유한 앵커 ID를 생성한다.
7. 복제본을 선택한 섹션 바로 다음 위치에 삽입한다.
8. GNB 표시 대상이면 GNB에 새로운 항목을 추가한다.
9. 복제 이후 원본과 복제본은 서로 독립적으로 수정한다.
10. 원본을 수정해도 복제본은 자동 변경되지 않고, 복제본을 수정해도 원본은 변경되지 않는다.

### 11.3 복제 개수 예시

```text
원본: 입지환경
복제본 1: 입지환경
복제본 2: 입지환경
복제본 3: 입지환경

총 4개 = 원본 1개 + 복제본 최대 3개
```

에디터 내부에서는 혼동을 줄이기 위해 `입지환경 · 복제 1` 같은 내부 식별 라벨을 표시할 수 있다. 공개 페이지의 실제 섹션 제목은 복제 시점에 원본과 동일하게 복사하며, 담당자가 별도로 수정할 수 있다.

### 11.4 데이터 복사 기준

```ts
type PageSection = {
  id: string;
  projectId: string;
  rootSectionId: string;
  sourceSectionId: string | null;
  sectionType: string;
  title: string;
  content: Record<string, unknown>;
  settings: Record<string, unknown>;
  isVisible: boolean;
  showInGnb: boolean;
  gnbLabel: string;
  anchorId: string;
  sortOrder: number;
  isOriginal: boolean;
  isRequired: boolean;
};
```

- JSON 콘텐츠와 설정은 깊은 복사를 사용한다.
- 이미지/영상 파일 자체는 불필요하게 중복 저장하지 않고 파일 레퍼런스를 복사할 수 있다.
- 파일 참조 개수를 관리해 다른 섹션이 사용하는 파일을 함께 삭제하지 않는다.
- 폼 ID, 앵커 ID, DB 기본키, 분석 이벤트 식별자는 새로 생성한다.
- 복제본끼리 다시 복제할 수 있다면 모두 동일한 최초 원본의 최대 3개 한도에 포함한다.

### 11.5 순서 변경

- 드래그 앤 드롭으로 섹션의 표시 순서를 변경.
- 키보드 사용자를 위한 대체 이동 동작 제공.
- 페이지 본문 렌더링 순서와 GNB 순서를 동일하게 변경.
- 작업본 저장 후 재발행하기 전까지 공개본 순서는 유지.

### 11.6 ON/OFF

- OFF인 섹션은 공개 페이지 본문에 표시하지 않는다.
- OFF인 섹션은 GNB에서도 자동으로 제거한다.
- ON으로 전환하면 현재 순서에 맞는 위치로 다시 표시한다.
- 섹션 콘텐츠는 OFF 상태에서도 보존한다.
- 폼이나 법적 고지 등 필수 섹션은 OFF 허용 여부를 정책으로 분리하고, 법적으로 필요한 고지가 사라지지 않도록 발행 검증을 수행한다.

### 11.7 삭제

- 복제본 삭제 가능.
- 삭제하면 관련 GNB 항목을 자동 제거.
- 원본 섹션은 기본적으로 삭제하지 않는다.
- 원본을 숨기는 경우 복제본까지 자동으로 숨길지는 독립 설정으로 처리하며, 기본값은 각각의 노출 상태를 유지.
- 다른 섹션이 공유하는 미디어 파일은 참조가 남아 있으면 삭제하지 않는다.

### 11.8 GNB 동기화 규칙

```text
GNB 항목 = 노출 중인 섹션 중 showInGnb가 true인 항목
정렬 순서 = 섹션 sortOrder
링크 대상 = 고유한 anchorId
```

- 복제 → GNB 항목 추가.
- 이동 → GNB 순서 변경.
- OFF → GNB 항목 제거.
- ON → GNB 항목 복구.
- 복제본 삭제 → GNB 항목 제거.
- GNB 라벨 변경 → 해당 항목만 변경.
- 동일한 제목의 섹션이 여러 개여도 `anchorId`는 반드시 달라야 한다.

## 12. 미디어 업로드와 파일 관리

### 12.1 지원 파일

- 히어로 이미지.
- 갤러리 이미지.
- 카드 / 설명용 이미지.
- 히어로 배경 영상.
- 영상 포스터 이미지.
- 필요 시 첨부형 브로슈어 또는 분양 안내 PDF.
- 생성된 성과 보고서 PDF.

### 12.2 업로드 요구사항

- 브라우저에서 오브젝트 스토리지로 직접 업로드하거나 안전한 서버 업로드 경로 사용.
- MIME 타입과 파일 확장자를 서버에서 모두 검증.
- 예측 가능한 공개 경로에 개인정보 포함 파일을 저장하지 않음.
- 업로드 상태, 실패, 재시도 표시.
- 이미지에는 alt 텍스트 입력 지원.
- 업로드한 파일이 실제로 저장된 후에만 작업본에 반영.
- 필요하면 이미지 썸네일 및 최적화 버전 생성.
- 대용량 영상은 스트리밍 가능한 형식 및 CDN 전달 방식 고려.
- 공개 페이지용 미디어와 내부 개인정보가 포함된 파일의 저장 버킷/권한 분리.

### 12.3 영상 동작

- 기본 음소거.
- 인라인 재생.
- 반복 재생 옵션.
- 모바일 및 저속 네트워크용 포스터 이미지.
- 사용자 `prefers-reduced-motion`을 존중하는 대체 표시.
- 영상 로드 실패 시 이미지 fallback.
- 첫 화면 성능을 해치지 않도록 영상 파일 크기와 프리로드 전략을 관리.

### 12.4 삭제와 참조 관리

- 하나의 파일을 여러 섹션이 참조할 수 있다.
- 파일 삭제 전에 실제 참조 수를 확인한다.
- 프로젝트 완전 삭제 시 프로젝트 전용 파일을 스토리지에서 삭제한다.
- CDN 캐시와 공개 링크 접근을 함께 정리한다.
- 시스템 전체의 기본 DB 비용이나 고정 서버 비용은 프로젝트 하나를 삭제했다고 자동으로 0원이 되지 않는다.

## 13. 작업본, 발행본, 버전 복구

### 13.1 데이터 분리

```text
작업본 draft
  └─ 편집기와 비공개 미리보기에서만 사용

공개본 published version
  └─ 실제 광고 URL과 검색엔진 응답에서만 사용
```

### 13.2 최초 발행

1. 프로젝트 필수 필드를 검증한다.
2. 공개 slug 중복 여부를 재확인한다.
3. 개인정보 동의 및 사업 주체 정보를 검증한다.
4. 작업본을 변경 불가능한 버전 스냅샷으로 저장한다.
5. 현재 공개 버전 포인터를 새 버전으로 변경한다.
6. `published_at` 및 `expires_at`을 계산한다.
7. 공개 캐시를 무효화하거나 새 버전으로 교체한다.
8. 발행자, 시각, 버전 번호를 감사 로그에 남긴다.

### 13.3 재발행

- 새 작업본 스냅샷을 생성.
- 현재 공개 버전을 새 버전으로 원자적으로 교체.
- 이전 공개본은 최근 버전 목록에 보존.
- 발행 처리 중 오류가 발생하면 기존 공개본을 유지.
- 발행 후 공개 URL을 별도로 바꾸지 않음.
- 수정 및 재발행 횟수는 제한하지 않음.

### 13.4 최근 5개 버전

- 최근 발행 스냅샷 최대 5개를 유지.
- 버전 번호, 발행 시각, 발행 직원, 변경 요약 표시.
- 선택한 과거 버전을 미리보기 가능.
- 복구 시 대상 버전을 새로운 작업본으로 가져오거나 새 공개 버전으로 재발행.
- 사용자의 확인 없이 공개 URL을 과거 버전으로 자동 전환하지 않음.
- 복구 후에도 전체 보관 개수는 최근 5개 범위 안에서 관리.

### 13.5 발행 전 검사

- 프로젝트명 존재.
- 사용 가능한 공개 URL.
- 선택된 템플릿.
- 필수 히어로 콘텐츠.
- 관심고객 폼 필수 필드 및 동의 문구.
- 개인정보 처리 주체와 실제 공개 정책.
- 광고주 수신자가 필요한 경우 인증 완료 수신자 존재.
- 법적 고지 및 문의 연락처.
- 만료일이 현재 시각 이후인지 확인.
- 이미지/영상 파일이 실제 저장소에 존재하는지 확인.

## 14. 운영기간, 만료, 연장, 삭제

### 14.1 기본값

```ts
const DEFAULT_PROJECT_DURATION_MONTHS = 3;
const EXPIRY_NOTICE_DAYS_BEFORE = 7;
const PROJECT_PURGE_GRACE_DAYS = 30;
const MAX_PUBLISHED_VERSIONS = 5;
const MAX_ADVERTISER_RECIPIENTS = 5;
const MAX_SECTION_COPIES_PER_ORIGINAL = 3;
```

### 14.2 운영기간 입력 UI

```text
운영기간
◉ 3개월
○ 직접 입력 [ N ] 개월
```

- 기본 선택은 반드시 `3개월`.
- 직접 입력은 1 이상의 정수.
- 임의의 작은 최대 개월 수를 제품 정책으로 강제하지 않는다.
- 오입력 방지를 위한 기술적 상한이 필요하면 환경설정으로 분리하고 UI에 안내.
- 월말 날짜 처리 규칙을 명확히 지정: 예를 들어 1월 31일 + 1개월이면 다음 달의 유효한 마지막 날짜를 사용.
- 기준 시간대는 `Asia/Seoul`.

### 14.3 시작일과 만료일

- 운영 시작일은 최초 발행 시각.
- `expires_at = 최초 발행 시각 + 운영개월 수`.
- 단순 작업본 생성만으로 운영기간을 차감하지 않음.
- 재발행이 자동으로 운영기간을 새로 시작하지 않음.
- 기간 변경 또는 연장은 별도의 명시적 액션으로 수행.

### 14.4 만료 7일 전 알림

- 광고사 담당자에게 발송.
- 해당 프로젝트의 광고주 수신자에게 발송.
- 광고주마다 선택한 알림 채널을 사용.
- 동일한 프로젝트·만료일에 중복 발송하지 않도록 idempotency key 사용.
- 연장으로 만료일이 바뀌면 변경된 만료일 기준으로 새 알림을 예약.
- 만료까지 7일 미만인 상태로 생성되거나 복구된 경우 알림 정책을 별도로 처리.

### 14.5 만료 시 처리

- 공개 페이지는 즉시 비공개.
- 공개 폼 접수 차단.
- 공개 페이지 응답에 기존 관심고객 데이터가 나타나지 않음.
- 검색엔진 및 CDN 캐시 정리.
- 관리자 목록에는 `만료됨` 표시.
- 연장 가능한 기간과 정리 예정일 표시.

### 14.6 수동 삭제

- 광고사 직원이 프로젝트를 직접 삭제할 수 있다.
- 삭제 확인창에서 현장명 또는 명시적인 확인을 요구.
- 삭제 즉시 공개 URL을 차단.
- 삭제한 직원과 시각을 기록.
- 파일, 버전, 리드, 통계, 백업은 데이터 유형별 보관정책에 따라 처리.

### 14.7 30일 정리와 개인정보 보관기간의 차이

`만료 30일 후 프로젝트 정리`와 `관심고객 개인정보 보관기간`은 같은 개념이 아니다.

- 프로젝트 공개본, 전용 미디어, 공개 캐시는 만료 후 30일에 정리한다.
- 관심고객 개인정보는 실제 수집 시 고지하고 동의받은 목적·기간에 따라 처리한다.
- 기존 기획 가이드의 `목적 종료 후 기본 6개월`은 **법률이 자동으로 허용하는 확정 기간이 아니며, 운영 기본안**이다.
- 6개월을 사용하려면 실제 처리 목적과 보관 근거를 검토하고 동의문에 표시해야 한다.
- 별도 보관 근거가 없으면 목적 달성 또는 삭제 요청 시 지체 없이 파기해야 한다.
- 프로젝트가 제거된 뒤에도 적법한 근거로 리드를 보관해야 한다면 최소한의 분리된 보관 구조와 접근 제한을 사용한다.
- 백업본은 즉시 수정이 어렵다면 복원 접근을 통제하고 정해진 회전 주기에 따라 삭제한다.

### 14.8 비용에 대한 운영 주의

- 특정 홈페이지를 삭제하면 해당 프로젝트의 파일 저장량, 영상 전송량, 발송량 등 변동비가 줄 수 있다.
- 반면 공통 DB, 호스팅 플랜, 도메인, 모니터링, 백업 등 고정비는 남을 수 있다.
- 따라서 `홈페이지를 삭제하는 순간 전체 서버비가 0원이 된다`고 안내하지 않는다.

- 방문 예정일: 날짜.

```ts
type LeadFormFieldType =
```

- 질문 제목.
- 안내 문구.
- 필수/선택 여부.
- 선택지 목록.
- 노출 순서.
- 공개 여부.
- 실제 저장되는 필드 키.
- 광고주 알림에 포함할지 여부.

### 15.5 전화번호 처리

- 한국 휴대전화 형식 중심 검증.
- 하이픈을 포함하거나 제외한 입력 모두 허용.
- 서버에서는 정규화된 문자열을 저장.
- 관리자와 광고주 알림에서는 읽기 쉬운 형식으로 표시.
- 마스킹하지 않는 표시는 권한이 있는 내부 화면과 인증된 수신자 알림으로 제한.
- 공개 페이지나 URL, 웹 분석 이벤트, 에러 로그에는 평문 전화번호를 노출하지 않음.

### 15.6 제출 처리

1. 공개 프로젝트 상태와 만료 여부 확인.
2. CSRF/Origin 검증 또는 동등한 공개 폼 보호.
3. 봇 차단을 위한 honeypot, rate limit 또는 필요 시 CAPTCHA.
4. 필수 필드 검증.
5. 동의 체크박스 서버 검증.
6. 현재 폼 버전과 동의 문구 버전 확인.
7. 리드 및 동의 스냅샷 저장.
8. 정상 접수 응답.
9. 비동기 알림 큐 등록.

### 15.7 중복 등록

- 같은 전화번호가 반복 등록되더라도 무조건 데이터를 삭제하지 않는다.
- 동일 프로젝트·동일 전화번호·짧은 시간 간격의 반복 제출은 중복 가능성으로 표시.
- 봇 또는 실수로 발생하는 초단기 반복은 속도 제한으로 차단.
- 중복 표시 기준은 운영 설정으로 관리하고 고객의 정상 문의를 임의로 누락하지 않는다.

### 15.8 제출 완료 화면

- `관심고객 등록이 완료되었습니다.`와 같은 명확한 확인.
- 실제 담당자 연락 예정 안내.
- 알림 발송 실패 여부를 고객에게 개인정보와 함께 공개하지 않음.
- 고객이 다시 제출해야 하는 상황을 만들지 않도록 저장 성공과 발송 실패를 분리.

- 메모 수정/삭제가 필요하면 작성자와 관리자 정책을 분리하고 변경 이력을 남김.

### 16.5 내보내기

- 운영상 필요하면 프로젝트별 Excel/CSV 다운로드를 지원.
- 내보내기는 권한 있는 직원만 가능.
- 다운로드한 직원, 프로젝트, 대상 건수, 시각을 감사 로그에 기록.
- 파일에 불필요한 내부 식별자나 동의 원문 전체를 넣지 않음.
- 대량 다운로드에는 추가 확인 또는 제한을 적용할 수 있음.

### 16.6 비식별 및 표시 정책

- 실무상 광고주가 직접 연락해야 하므로 인증된 수신자에게 이름과 연락처를 평문으로 제공 가능.
- 관리자 로그인 이후 권한 있는 광고사 직원도 평문 확인 가능.
- 모니터링 로그, analytics payload, 브라우저 콘솔, 서버 오류 수집에는 평문 개인정보를 넣지 않음.
- 공개 API 응답은 다른 사용자의 리드 정보를 반환하지 않음.

## 17. 광고주 수신자 설정

### 17.1 프로젝트당 최대 5명

```ts
const MAX_ADVERTISER_RECIPIENTS = 5;
```

- 서로 다른 담당자 5명까지 등록 가능.
- 비활성화된 담당자를 포함한 개수 계산 방식은 UI에 명확히 표시.
- 권장 정책: 동시에 활성화된 수신자 최대 5명.

### 17.2 수신자 필드

| 필드 | 설명 |
| --- | --- |
| 이름 | 광고주 담당자 이름 |
| 소속 / 회사명 | 실제 정보를 전달받는 광고주 조직 |
| 휴대전화 번호 | 알림톡 및 필요한 경우 SMS 인증 |
| 이메일 주소 | 이메일 선택 시 필수 |
| 기본 알림 채널 | `KAKAO_ALIMTALK` 또는 `EMAIL` |
| 관심고객 알림 수신 | 기본 활성 |
| 만료 예정 알림 수신 | 기본 활성 |
| 인증 상태 | 전화 또는 이메일 소유 확인 결과 |
| 활성 상태 | 발송 가능 여부 |
| 생성/변경 이력 | 누가 언제 등록 또는 변경했는지 |

### 17.3 수신 채널

```text
◉ 카카오 알림톡
○ 이메일
```

- 기본 선택은 카카오 알림톡.
- 광고주 담당자마다 개별 선택.
- 이메일을 선택한 담당자에게는 이메일 발송.
- 한 명에게 모든 채널을 무조건 동시에 발송하지 않음.
- 향후 `둘 다 수신` 옵션이 필요하면 별도 확장으로 추가.

### 17.4 인증

- 알림톡 수신 번호는 휴대전화 소유 확인 또는 동등한 운영 검증 절차를 거침.
- 이메일 수신자는 인증 메일의 링크를 확인.
- 검증되지 않은 연락처에는 관심고객 개인정보를 보내지 않음.
- 연락처 또는 이메일을 수정하면 기존 인증 상태를 무효화하고 재인증.
- 수신자 등록, 변경, 인증, 비활성화 기록을 보관.

### 17.5 수신자 부재

- 인증 완료된 광고주 수신자가 없으면 발행 전 또는 리드 수집 시작 전에 경고.
- 고객 리드 저장 자체를 실패시킬지 여부는 운영 정책으로 구분.
- 권장 기본값: 리드는 안전하게 저장하되 관리자에게 `수신자 미설정` 경고를 명확히 표시.
- 발송 설정이 완료된 뒤 과거 리드를 자동으로 일괄 재발송하지 말고 담당자 확인 후 처리.

## 18. 카카오 알림톡, 이메일, 선택적 문자 대체 발송

### 18.1 알림톡의 성격

- 알림톡은 실제 서비스 이용과 관련된 **정보성 메시지**에 사용한다.
- 신규 관심고객 접수 안내와 운영 만료 안내는 실제 계약 및 업무 관계를 기반으로 구성한다.
- 할인 문구, 이벤트 홍보, 신규 상품 권유 등 광고성 내용을 정보성 알림톡에 섞지 않는다.
- 광고성 발송이 필요하면 별도의 수신동의와 카카오의 광고성 메시지 정책을 검토한다.
- 실제 알림톡 발송은 공식 발송 대행사 또는 적법한 메시징 공급자 연동이 필요하다.
- 브랜드 채널명과 사업자 정보가 확정되기 전에는 샌드박스 또는 목업 어댑터로 개발한다.

### 18.2 신규 관심고객 알림 예시

```text
[신규 관심고객 등록]

현장명: 루미에르 센트럴
이름: 홍길동
연락처: 010-1234-5678
관심 타입: 84㎡
문의 내용: 방문 상담 일정을 알고 싶습니다.
접수 시각: 2026.08.21 14:30

본 정보는 해당 현장 상담 목적으로만 이용해 주세요.
무단 공유, 다른 현장 활용 또는 목적 외 사용은 금지됩니다.
```

### 18.3 만료 7일 전 안내 예시

```text
[홈페이지 운영 만료 예정]

현장명: 루미에르 센트럴
공개 주소: https://example.com/lumiere-central
운영 종료일: 2026.11.21
남은 기간: 7일

운영 연장이 필요하면 담당 광고사에 문의해 주세요.
```

### 18.4 발송 대상

| 이벤트 | 광고사 담당자 | 광고주 담당자 | 비고 |
| --- | --- | --- | --- |
| 신규 관심고객 등록 | 관리자 화면에서 확인 | 즉시 발송 | 광고주에게만 신규 리드 알림 발송 |
| 만료 7일 전 | 발송 | 발송 | 양측 모두 안내 |
| 알림 실패 경고 | 관리자 화면에 표시 | 필요 시 대체 채널 | 정책 기반 |
| 직원 초대 | 대상 직원에게 메일 | 해당 없음 | 인증용 이메일 |

### 18.5 이메일 발송

- 광고주별 이메일 선택 가능.
- 제목에 현장명 및 문의 등록 사실을 표시.
- 모바일에서 읽기 쉬운 HTML / 텍스트 본문 구성.
- 인증된 이메일 주소에만 발송.
- 메일 본문에 목적 외 이용 금지 안내 포함.
- 실제 발송 성공 여부는 공급자 응답 및 callback/webhook 기준으로 기록.

### 18.6 SMS 대체 발송

- 초기 기본 채널은 알림톡 또는 이메일이다.
- 알림톡 실패 시 문자 대체 발송은 운영상 선택 가능한 확장 기능이다.
- SMS 발송을 사용하려면 실제 발신번호 등록, 비용, 발송 정책, 개인정보 노출 수준을 확인한다.
- 담당자가 허용하지 않은 상태에서 실패한 알림톡을 자동으로 임의의 번호에 문자로 보내지 않는다.
- 문자 대체 발송이 비활성인 경우 관리자에게 실패 경고와 수동 재시도 기능을 제공한다.

### 18.7 비동기 발송 및 재시도

```text
리드 저장 성공
   ↓
notification_jobs 생성
   ↓
작업 큐 처리
   ↓
카카오 / 이메일 공급자 발송
   ↓
성공 / 실패 / 재시도 결과 기록
```

- 리드 저장과 알림 발송을 분리.
- 리드 저장과 발송 작업 생성은 가능하면 같은 DB 트랜잭션의 transactional outbox로 처리.
- 공급자 장애가 있어도 리드 데이터는 유실되지 않음.
- 각 수신자와 이벤트마다 고유한 idempotency key 생성.
- 제한된 횟수의 지수 백오프 재시도.
- 최종 실패 시 관리자 로그에 표시.
- 동일 callback이 여러 번 도착해도 상태를 안전하게 처리.
- 수신자가 비활성화되면 예약된 작업을 중단.

### 18.8 조용한 시간 설정

- 사용자가 별도의 방해금지 시간은 필요 없다고 확정했다.
- 그러나 실제 발송 메시지가 정보성이 아닌 광고성으로 분류된다면 해당 법령과 발송 채널 정책이 제품 설정에 우선한다.
- 초기에는 **업무상 필요한 정보성 알림**만 구현하고, 무차별 광고 발송 기능은 만들지 않는다.

## 19. 개인정보, 동의, 보안

### 19.1 가장 중요한 원칙

- 개인정보 수집 주체를 실제 회사명으로 명확히 표시해야 한다.
- `광고사`, `광고주`, `운영사`처럼 일반명칭만 적고 누가 처리하는지 숨기지 않는다.
- 광고사, 플랫폼 운영 법인, 광고주가 서로 다른 법인인지에 따라 수집 주체, 수탁자, 제3자 제공 대상이 달라질 수 있다.
- 개인정보 처리방침과 실제 동의문은 법인명 확정 후 전문 검토를 거친다.
- 법인명과 처리 주체가 아직 없는 경우 샘플 데이터로 개발하되, 실제 고객 데이터 수집은 차단한다.

### 19.2 권장 법적 정보 모델

```ts
type ProjectPrivacyConfig = {
  collectingControllerName: string;
  operatingCompanyName: string;
  advertisingAgencyName: string;
  advertiserCompanyName: string;
  collectionPurpose: string;
  collectedFields: string[];
  retentionDescription: string;
  privacyPolicyUrl: string;
  thirdPartyProvisionEnabled: boolean;
  thirdPartyRecipientName?: string;
  thirdPartyPurpose?: string;
  thirdPartyFields?: string[];
  thirdPartyRetentionDescription?: string;
  refusalConsequence: string;
  privacyContactEmail?: string;
};
```

### 19.3 수집·이용 동의에 포함할 정보

- 개인정보를 수집하는 실제 주체.
- 수집 목적: 해당 분양 현장의 상담 및 문의 응대.
- 수집 항목: 이름, 연락처, 문의 내용, 선택 질문 등.
- 보유 및 이용기간.
- 동의를 거부할 권리.
- 동의를 거부할 경우 문의 접수 또는 상담이 제한될 수 있다는 안내.

### 19.4 제3자 제공 동의

광고주가 수집 주체와 다른 별도 개인정보 처리자라면, 법적 검토 결과에 따라 수집·이용 동의와 구분된 제3자 제공 동의를 구현한다.

포함 항목:

- 제공받는 회사의 실제 명칭.
- 제공받는 회사의 이용 목적.
- 제공되는 개인정보 항목.
- 제공받는 회사의 보유 및 이용기간.
- 동의 거부 권리와 거부 시 영향.

중요:

- 광고주 담당자 5명의 이름을 모두 별개의 제3자 법인처럼 표시하는 것은 적절하지 않을 수 있다.
- 실제로 정보를 제공받는 법인과 그 법인에 소속된 인증된 담당자를 구분한다.
- 광고사가 광고주의 수탁자로 처리하는지, 광고주에게 제3자 제공하는지는 실제 계약관계와 법률 검토에 따라 확정한다.
- 자동으로 모든 프로젝트를 동일한 법적 구조로 간주하지 않는다.

### 19.5 체크박스 동작

```text
□ [필수] 개인정보 수집 및 이용에 동의합니다. [내용 보기]
□ [필수] 개인정보 제3자 제공에 동의합니다. [내용 보기]
```

- 제3자 제공 동의는 실제로 필요한 프로젝트에만 표시.
- 기본 체크 상태 금지.
- 동의 항목을 하나로 뭉개지 않음.
- 체크하지 않으면 제출 불가.
- `내용 보기`에서 실제 주체, 목적, 항목, 기간을 확인 가능.
- 마케팅 수신 동의가 필요하면 선택 동의로 분리하되 초기에는 구현하지 않음.

### 19.6 동의 증빙 저장

```ts
type ConsentSnapshot = {
  leadId: string;
  consentType: 'COLLECTION' | 'THIRD_PARTY_PROVISION';
  consentVersion: string;
  consentTextSnapshot: string;
  consentTextHash: string;
  agreedAt: string;
  ipEvidence: string | null;
  userAgent: string | null;
};
```

- 제출 시점의 실제 동의문 원문 또는 검증 가능한 스냅샷 저장.
- 동의 버전, 해시, 시각 기록.
- IP 및 사용자 에이전트는 필요한 최소 범위만 저장하고 보관기간을 설정.
- 이후 동의문을 수정해도 기존 동의 증빙이 조용히 바뀌지 않음.

### 19.7 접근통제

- 로그인한 조직 구성원만 해당 조직의 리드 조회.
- 정지된 사용자의 접근 즉시 차단.
- 광고주 수신자는 서비스 로그인 없이, 검증된 알림 채널에서만 정보를 받음.
- 리드 조회, 내보내기, 수신자 변경, 삭제를 감사 로그에 기록.
- 서비스 롤 권한은 서버 환경에서만 사용.
- DB Row Level Security 또는 동등한 서버 측 권한검증 적용.

### 19.8 암호화와 민감 데이터

- 모든 네트워크 통신 HTTPS.
- DB 및 백업 저장 시 공급자 암호화 설정 확인.
- 전화번호, 이메일, 토큰 등은 노출 위험을 고려해 필드 단위 보호를 검토.
- 연락처 검색이 필요하면 평문 전화번호를 검색 인덱스에 노출하기보다 서버 비밀키 기반 HMAC 검색 해시를 검토.
- 권한 확인을 통과한 서버에서만 복호화해 광고사 화면과 인증된 광고주 알림에 표시.
- 알림 공급자 키, DB 서비스 키, 스토리지 비밀 키는 시크릿으로 관리.
- Git 저장소에 `.env`, 실제 고객 데이터, 토큰을 커밋하지 않음.
- 오류 리포팅 도구에 평문 전화번호나 전체 메시지 본문을 보내지 않음.

### 19.9 파기

- 설정된 개인정보 보관 만료일에 자동 파기 작업 실행.
- 고객이 삭제를 요청하면 법적 의무 보관을 제외하고 적절히 처리.
- 파기 결과와 실행 시각을 로그에 기록.
- 통계는 필요한 경우 개인을 식별할 수 없는 집계값만 보존.
- 파일, 메모, 알림 payload, 큐, 캐시, 백업에서의 보관 범위를 함께 검토.

### 19.10 서비스 외부 경계

- 직방 DB, 직방 클라우드, 직방 계정, 직방 사내 고객 데이터에 접근하지 않는다.
- 직방 소스코드나 사내 기획문서에서 비공개 자산을 가져오지 않는다.
- 도메인만 별도로 두고 실제 개인정보를 직방 인프라에 저장하는 구조를 사용하지 않는다.
- 현직 회사의 겸업, 영업비밀, 지식재산, 보안 규정을 사용자와 운영 측이 별도로 확인해야 한다.

## 20. 유입 추적 및 분석

### 20.1 핵심 KPI

- 전체 조회수: `page_view`.
- 순 방문자 수: `unique_visitor`.
- 전화 버튼 클릭 수: `phone_click`.
- 관심고객 CTA 클릭 수: `lead_cta_click`.
- 폼 작성 시작 수: `lead_form_start`.
- 관심고객 등록 완료 수: `lead_submit_success`.
- 전환율: `관심고객 등록 완료 / 순 방문자` 또는 선택한 분모 기준을 명시.
- 유입 매체별 성과.
- 디바이스별 성과.
- 일자별 방문 및 전환 추이.

### 20.2 추적 이벤트 예시

```ts
type AnalyticsEventName =
  | 'page_view'
  | 'session_start'
  | 'gnb_click'
  | 'section_view'
  | 'phone_click'
  | 'lead_cta_click'
  | 'lead_form_start'
  | 'lead_submit_success'
  | 'lead_submit_error';
```

### 20.3 이벤트 속성

```ts
type AnalyticsEvent = {
  organizationId: string;
  projectId: string;
  publishedVersionId: string | null;
  eventName: AnalyticsEventName;
  occurredAt: string;
  anonymousSessionId: string;
  anonymousVisitorId: string | null;
  referrer: string | null;
  utmSource: string | null;
  utmMedium: string | null;
  utmCampaign: string | null;
  utmContent: string | null;
  utmTerm: string | null;
  deviceType: 'mobile' | 'desktop' | 'tablet' | 'unknown';
  metadata: Record<string, string | number | boolean | null>;
};
```

### 20.4 개인정보 주의

- 이벤트 payload에 관심고객 이름, 전화번호, 이메일, 문의 원문을 저장하지 않는다.
- URL 쿼리스트링으로 전화번호나 이름을 전달하지 않는다.
- 제3자 분석도구를 사용한다면 개인정보 처리방침과 쿠키 정책에 실제 사용 내용을 반영한다.
- 가급적 내부 집계 또는 개인정보 최소화 중심 분석 구조를 우선 검토한다.

### 20.5 UTM 처리

- 최초 유입 시 UTM source, medium, campaign, content, term 저장.
- 관심고객 등록 시 해당 세션의 유입 정보를 리드와 연결.
- 직접 유입은 `direct` 또는 동등한 값으로 정규화.
- 누락된 UTM 때문에 리드 제출이 실패하지 않도록 처리.
- 네이버, 카카오, 메타, 구글 등 채널명은 원본값과 표시용 라벨을 분리.

### 20.6 분석 화면

- 기간 선택: 오늘, 최근 7일, 최근 30일, 직접 지정.
- KPI 카드.
- 일별 방문 / 전환 추이 그래프.
- 유입 채널별 표.
- UTM 캠페인별 표.
- 디바이스별 비중.
- 전화 클릭 및 관심고객 전환율.
- PDF 보고서 다운로드.

### 20.7 외부 광고 추적 코드 / 식별자

광고사 실무에서 외부 매체의 추적 식별자, 태그 ID 또는 검증 코드가 필요한 경우를 대비해 프로젝트별 분석 설정을 확장 가능하게 설계한다.

```ts
type ProjectTrackingConfig = {
  internalAnalyticsEnabled: boolean;
  googleAnalyticsMeasurementId?: string;
  googleTagManagerContainerId?: string;
  metaPixelId?: string;
  customVerificationCode?: string;
};
```

- 직방의 특정 해시 코드나 내부 구현을 그대로 복사하지 않는다.
- 식별자 기반의 정해진 공급자 연동을 우선하고, 사용자가 임의 JavaScript를 직접 삽입하는 기능은 기본으로 허용하지 않는다.
- 허용할 추적 공급자는 운영 측이 선택하고 화이트리스트로 관리한다.
- 외부 추적 도구를 활성화하기 전에 개인정보 처리방침, 쿠키, 제3자 전송 범위를 검토한다.
- 리드의 이름, 연락처, 문의 원문을 추적 코드로 전송하지 않는다.
- 직접 운영하는 서버 기반 분석만으로도 핵심 통계가 동작하도록 하고, 외부 태그는 선택적 확장으로 분리한다.

### 22.3 타이포그래피 권장값

| --- | --- | --- | --- |
| 주요 화면 제목 | 30~36px | 700 | 약 1.4~1.5 |

| 작은 메타 정보 | 12~13px | 400~500 | 충분한 가독성 확보 |

### 22.4 버튼

- 기본 액션: 파란색 배경 + 흰색 텍스트.
- 보조 액션: 연한 파란색 배경 + 파란 텍스트.
- 삭제/정지: 명확한 danger 스타일과 확인 단계.
- 로딩, disabled, hover, pressed, focus-visible 상태 구현.
- 로딩 중 버튼 폭이 갑자기 바뀌지 않도록 처리.
- 모바일 주요 CTA는 충분한 터치 높이 확보.
- 데스크톱 관리자 버튼과 모바일 랜딩 CTA의 크기를 무조건 동일하게 강제하지 않음.

### 22.5 입력폼

- 레이블, 도움말, 오류 메시지 제공.
- focus, error, disabled, read-only 상태 제공.
- 오류가 발생한 필드를 명확히 설명.
- 전화번호와 이메일 등은 실제 형식에 맞는 키보드 및 autocomplete 설정.
- 동의 체크박스는 내용 확인과 선택 상태가 분명해야 함.

### 22.6 레이아웃 원칙

- 간격은 4/8/16/24/32px 계열을 기본 작업 단위로 사용.
- 관계 있는 제목, 설명, 액션은 가까이 배치.
- 시각적 이유 없이 큰 빈 공간을 남기지 않음.
- 카드 안의 콘텐츠가 지나치게 작거나 한쪽에 몰리지 않도록 균형 있게 배치.
- 화살표를 빈 공간에 떠 있게 두지 않고 실제 연결 관계가 있을 때만 사용.
- 상태 배지는 의미가 있는 실제 상태에만 사용.
- `READY`처럼 사용자에게 설명할 수 없는 장식용 라벨 사용 금지.
- 표, 카드, 헤더, 아이콘, 버튼의 수평/수직 정렬 일관성 확보.
- 작은 화면에서 텍스트 겹침, 잘림, 과도한 여백이 없도록 검증.

### 22.7 접근성

- 키보드로 메뉴, 토글, 모달, 드래그 대체 동작에 접근 가능.
- 충분한 텍스트 대비.
- 의미 있는 `aria-label`.
- 모달 focus trap 및 닫기 동작.
- 이미지 alt 텍스트.
- 토글과 체크박스의 현재 상태를 보조기술이 인식 가능.
- `prefers-reduced-motion` 지원.

### 23.1 기본 스택

| 영역 | 권장 선택 | 선택 이유 |
| --- | --- | --- |

| 파일 | S3 호환 Object Storage / Cloudflare R2 / Supabase Storage | 이미지·영상·PDF 관리 |
| 배포 | Vercel 또는 동등한 관리형 배포 | 초기 운영 부담 축소 |
| 폼 검증 | React Hook Form + Zod 또는 동등한 조합 | 입력 검증과 타입 안정성 |
| 편집기 상태 | Zustand 또는 동등한 상태 관리 | 작업본 편집 및 저장 상태 |
| 드래그 정렬 | dnd-kit 또는 동등한 라이브러리 | 섹션 순서 변경 |
| 서버 데이터 | TanStack Query 또는 프레임워크 기본 기능 | 캐시, 로딩, 동기화 |
| 차트 | Recharts 또는 동등한 차트 라이브러리 | 통계와 보고서 시각화 |
| 큐/스케줄 | 관리형 큐, Cron, DB 작업 큐 중 하나 | 발송 재시도, 만료 및 파기 |
| 이메일 | 검증된 메일 발송 공급자 | 초대 및 광고주 알림 |
| 알림톡 | 공식 딜러사 또는 대행사 API | 카카오 정보성 알림 발송 |
| 테스트 | Vitest/Jest + Playwright 또는 동등한 조합 | 핵심 정책 및 E2E 검증 |

라이브러리의 정확한 버전은 프로젝트 생성 시 공식 문서를 기준으로 확인한다. 이 문서에서 검증되지 않은 특정 최신 버전을 임의로 고정하지 않는다.

### 23.2 초기 구조 원칙

- 처음부터 AWS 전체 서비스를 직접 운영할 필요는 없다.
- 인증, DB, 파일, 메시징, 분석, 백업 모듈을 코드에서 분리한다.
- 공급자별 SDK를 UI 컴포넌트에 직접 섞지 않는다.
- 공개 페이지와 관리자 화면은 동일한 코드베이스 안에서 경계를 분리한다.
- 환경변수만 바꿔도 개발/스테이징/운영 구성이 분리되도록 설계한다.

### 23.3 AWS 전환 검토 시점

- 월 단위 사이트 수가 수백 개 수준으로 증가.
- 영상 파일과 CDN 전송량이 크게 증가.
- 대형 광고주가 별도 보안 또는 네트워크 요건을 요구.
- 관리형 서비스 월비용이 지속적으로 높아져 구조적인 절감 검토가 필요.
- DB 성능, 큐 처리량, 백업/감사 요구가 현재 공급자의 한계를 초과.

기존 기획 가이드의 `월 70만 원 이상 지속`은 사업 검토를 시작할 수 있는 **참고 기준**이며, 모든 서비스에 적용되는 자동 이전 조건은 아니다.

### 24.2 서버와 클라이언트 경계

- 공개 페이지 조회는 발행된 버전만 조회.
- 관리자 데이터는 인증된 서버 컴포넌트 또는 보호된 API로 조회.
- 서비스 롤 권한은 server-only 모듈에서만 사용.
- 프런트엔드에서 role이나 organization_id를 변경했다고 실제 권한이 바뀌지 않도록 처리.
- 공개 폼 제출 API는 리드 생성만 허용하며 다른 리드 조회 권한을 제공하지 않음.

### 25.20 DB 무결성

- `duration_months >= 1`.
- 활성 수신자 최대 5명.
- 원본 섹션당 복제본 최대 3개.
- 공개 slug 중복 불가.
- 섹션 anchor ID 중복 불가.
- 동의 없는 리드 생성 불가.
- 조직 외 데이터 접근 불가.
- 마지막 활성 시스템 관리자 정지 불가.
- 발행 버전은 프로젝트와 조직이 일치해야 함.
- 서버 검증 없이 프런트엔드 버튼만 비활성화하는 것으로 정책을 대신하지 않음.
- 섹션 복제와 수신자 등록은 동시 요청이 들어와도 한도를 넘지 않도록 DB 트랜잭션, 잠금 또는 동등한 원자적 제약으로 처리.
- 리드 저장과 알림 작업 생성은 같은 트랜잭션에서 처리하거나 outbox로 정합성을 보장.
- 개인정보 평문 표시는 UI 요구사항이지 DB에 연락처를 평문 저장하라는 의미가 아님.

### 25.21 조직 단위 접근제어 예시

```sql
-- 개념 예시: 현재 사용자가 해당 organization_id의 활성 멤버인지 검사.
-- 실제 함수명과 auth.uid() 사용법은 선택한 인증 공급자에 맞춰 구현한다.

CREATE POLICY organization_members_can_read_own_projects
ON projects
FOR SELECT
USING (
  EXISTS (
    SELECT 1
    FROM organization_members AS member
    WHERE member.organization_id = projects.organization_id
      AND member.user_id = auth.uid()
      AND member.status = 'ACTIVE'
  )
);
```

- 프로젝트뿐 아니라 작업본, 버전, 섹션, 리드, 메모, 수신자, 알림, 파일 메타데이터에도 동일한 조직 경계를 적용한다.
- 관리자 전용 작업은 활성 멤버 여부 외에 역할을 추가 검사한다.
- 공개 랜딩페이지와 공개 리드 생성은 제한된 서버 경로에서만 처리하고 전체 테이블 공개 권한을 부여하지 않는다.

## 27. 배포, 운영, 백업

### 27.1 개발 환경 구분

```text
local       개발자 로컬 환경
staging     내부 테스트 / 데모 환경
production  실제 운영 환경
```

- 환경별 DB, 저장소, 도메인, 알림 수신 대상을 분리.
- staging에서 실제 광고주에게 고객 정보를 잘못 보내지 않도록 발송 차단 또는 테스트 수신자 강제.
- 샘플 데이터와 실제 개인정보를 명확히 구분.

### 27.2 배포 체크리스트

- HTTPS 활성화.
- 서비스 도메인 연결.
- 관리자 호스트와 공개 호스트 라우팅 확인.
- 운영 DB migration 적용.
- 파일 저장소 및 CORS 설정.
- 조직별 권한과 RLS 확인.
- 이메일 발신 도메인 인증.
- 알림톡 공식 발송 공급자 연결.
- cron / queue 동작 확인.
- 오류 모니터링 및 경보 연결.
- 백업 및 복구 테스트.
- 실제 개인정보 처리방침과 법적 주체 설정.
- 운영 관리자 계정 생성.

### 27.3 백업

- DB 자동 백업.
- 저장소 파일 복구 가능성 확인.
- 중요 설정 및 인프라 구성 문서화.
- 최소 1회 복구 리허설.
- 백업 보관기간과 개인정보 파기 정책의 정합성 검토.
- 장애 복구 절차와 연락 담당자를 정리.

### 27.4 모니터링

- 로그인 실패 급증.
- 공개 페이지 오류.
- 관심고객 폼 제출 실패.
- 알림톡/이메일 발송 실패.
- 만료 처리 작업 실패.
- 개인정보 파기 작업 실패.
- 비정상적인 리드 대량 조회 또는 다운로드.
- 스토리지 사용량 및 영상 트래픽 증가.

### 27.5 비상 비공개

- 광고사 직원이 법적 문제 또는 현장 운영 이슈가 발생하면 프로젝트를 즉시 비공개할 수 있어야 한다.
- 비공개 후 기존 URL은 신규 문의를 받지 않아야 한다.
- 실행자, 시각, 사유를 로그로 남길 수 있어야 한다.
- 별도 승인 절차는 필요하지 않다.

## 32. 테스트 계획과 인수 기준

### 32.1 인증 및 권한

- [ ] 초대받지 않은 사용자는 계정을 직접 생성할 수 없다.
- [ ] 초대받은 직원은 계정을 활성화하고 로그인할 수 있다.
- [ ] 정지된 계정은 즉시 로그인이 차단된다.
- [ ] 정지된 계정의 기존 세션도 보호된 요청에서 거부된다.
- [ ] 마지막 활성 시스템 관리자는 정지할 수 없다.
- [ ] 같은 조직 직원은 모든 프로젝트와 리드를 공동 조회한다.
- [ ] 다른 조직의 프로젝트 ID를 직접 입력해도 조회할 수 없다.

### 32.2 프로젝트와 URL

- [ ] 프로젝트명이 아닌 별도 입력값으로 URL을 만든다.
- [ ] 한글, 영문, 숫자, 하이픈 URL이 동작한다.
- [ ] 중복된 URL이 차단된다.
- [ ] 예약어 URL이 차단된다.
- [ ] 기본 운영기간이 3개월로 선택되어 있다.
- [ ] 직접 입력한 N개월이 정상 반영된다.
- [ ] 프로젝트 목록에서 상태와 만료일을 확인한다.

### 32.3 템플릿과 편집기

- [ ] 신규 템플릿이 2종 제공된다.
- [ ] FAQ 섹션이 없다.
- [ ] 히어로 이미지를 업로드할 수 있다.
- [ ] 영상 지원 템플릿에서 영상을 업로드할 수 있다.
- [ ] 영상 로드 실패 시 포스터 이미지가 표시된다.
- [ ] `섹션 추가` 버튼이 없다.
- [ ] 기존 섹션을 복제할 수 있다.
- [ ] 원본당 최대 3개까지만 복제할 수 있다.
- [ ] 복제 직후 문구, 이미지, 설정이 동일하다.
- [ ] 복제 후 수정은 원본과 독립적이다.
- [ ] 섹션 순서를 변경할 수 있다.
- [ ] 섹션을 ON/OFF할 수 있다.
- [ ] 복제본을 삭제할 수 있다.
- [ ] GNB 항목이 순서와 표시 상태에 맞게 동기화된다.
- [ ] 같은 제목의 복제본에도 고유한 앵커가 생성된다.
- [ ] PC 및 모바일 미리보기가 정상 동작한다.

### 32.4 발행과 복구

- [ ] 최초 발행 전 공개 URL은 노출되지 않는다.
- [ ] 최초 발행 후 공개 URL이 정상 표시된다.
- [ ] 작업본 수정만으로 공개본이 바뀌지 않는다.
- [ ] 재발행 후에만 공개 URL이 변경된다.
- [ ] 재발행 횟수에 제한이 없다.
- [ ] 최근 5개 발행 버전만 확인할 수 있다.
- [ ] 선택한 버전을 명시적으로 복구할 수 있다.
- [ ] 발행 실패 시 기존 공개본이 유지된다.

### 32.5 관심고객

- [ ] 이름과 연락처가 필수다.
- [ ] 관심 타입 선택형 질문을 구성할 수 있다.
- [ ] 문의 내용과 추가 질문을 프로젝트별로 조정할 수 있다.
- [ ] 수집·이용 동의를 체크하지 않으면 등록할 수 없다.
- [ ] 필요한 경우 제3자 제공 동의를 별도로 받는다.
- [ ] 동의 원문 버전과 시각이 저장된다.
- [ ] 리드 목록에서 이름, 연락처, 현장, 등록일을 확인한다.
- [ ] 리드에 여러 개의 누적 메모를 남길 수 있다.
- [ ] 상담 상태 단계 관리 기능은 없다.
- [ ] 리드 내보내기 시 접근 로그가 남는다.

### 32.6 광고주 알림

- [ ] 프로젝트당 활성 광고주 수신자를 최대 5명까지 등록한다.
- [ ] 6번째 활성 수신자는 등록할 수 없다.
- [ ] 수신자마다 알림톡 또는 이메일을 선택할 수 있다.
- [ ] 기본 채널은 카카오 알림톡이다.
- [ ] 인증되지 않은 연락처에는 발송하지 않는다.
- [ ] 리드 등록 즉시 광고주에게 해당 정보를 발송한다.
- [ ] 이름과 전화번호는 인증된 수신자에게 마스킹 없이 표시할 수 있다.
- [ ] 목적 외 이용 금지 문구를 함께 전달한다.
- [ ] 알림 실패 시 리드 자체는 정상 저장된다.
- [ ] 실패 결과와 재시도 이력이 기록된다.

### 32.7 만료와 삭제

- [ ] 만료 7일 전 광고사와 광고주 모두에게 알림을 보낸다.
- [ ] 동일한 만료일에 중복 알림이 발송되지 않는다.
- [ ] 프로젝트 기간을 직접 연장할 수 있다.
- [ ] 만료 시 공개 URL이 비공개 처리된다.
- [ ] 만료 후 신규 관심고객을 등록할 수 없다.
- [ ] 광고사가 홈페이지를 직접 삭제할 수 있다.
- [ ] 문제 발생 시 즉시 수동 비공개할 수 있다.
- [ ] 만료 후 30일 정리 일정이 반영된다.
- [ ] 개인정보 파기는 실제 동의 및 보관정책과 일치한다.

### 32.8 분석과 리포트

- [ ] 페이지 조회수를 확인한다.
- [ ] 순 방문자 수를 확인한다.
- [ ] 전화 클릭 수를 확인한다.
- [ ] 관심고객 등록 수와 전환율을 확인한다.
- [ ] UTM 유입 경로를 확인한다.
- [ ] 추적 식별자 연동 시 임의 스크립트 실행이나 전화번호 유출이 발생하지 않는다.
- [ ] 날짜별 방문/전환 그래프를 확인한다.
- [ ] 디바이스별 데이터를 확인한다.
- [ ] 광고주 공유용 PDF를 다운로드한다.
- [ ] PDF 및 관리자 UI에 Pretendard가 적용된다.
- [ ] analytics 이벤트에 전화번호나 문의 원문이 포함되지 않는다.

### 32.9 운영 배포

- [ ] 실제 DB를 사용한다.
- [ ] 실제 인증 세션을 사용한다.
- [ ] 실제 파일 저장소에 업로드한다.
- [ ] production과 staging 발송 대상을 분리한다.
- [ ] 알림톡 공급자 연동이 준비되어 있다.
- [ ] 만료/파기 스케줄 작업이 실제 실행된다.
- [ ] 개인정보 처리방침과 법적 처리 주체가 실제 정보로 설정되어 있다.
- [ ] 보안 키가 브라우저와 Git에 노출되지 않는다.
- [ ] 백업 및 복구 절차가 검증되어 있다.

## 33. Cursor 작업 지시 템플릿

### 33.1 첫 번째 지시

```text
첨부된 CURSOR-landing-platform-development-spec.md 파일을 전체 읽고,
제품 요구사항, 금지 기능, 데이터 구조, 개인정보 정책을 먼저 이해해.

지금은 전체 기능을 한 번에 무작정 구현하지 말고 다음을 먼저 수행해.

1. 현재 저장소 구조와 사용 중인 프레임워크를 확인.
2. 문서와 현재 코드 사이의 차이점을 정리.
3. Phase 0~7을 구현 가능한 작업 단위로 분해.
```
